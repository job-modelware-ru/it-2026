# Описание БД «Подъезд Онлайн»

Команда 14. База данных приложения «Подъезд Онлайн». Для целевой системы в [нефункциональных требованиях](../03-Системный%20аналитик/Нефункциональные%20требования.md) указана PostgreSQL. Локальное демо пока использует JSON; SQL-файлы ниже создают отдельную учебную БД и не переводят демо на PostgreSQL.

- [Логическая схема](Логическая%20схема.md) описывает сущности и их связи.
- [Физическая схема](Физическая%20схема.md) задаёт таблицы, типы, ключи, ограничения и индексы.

## SQL-файлы и запуск

Структура каталога повторяет пример преподавателя:

```text
05-Архитектор БД/
├── Логическая схема.md
├── Физическая схема.md
├── Описание БД.md
└── sql/
    ├── 01_create_database.sql
    ├── 02_test_data.sql
    └── 03_queries.sql
```

В pgAdmin нужно создать пустую базу `podezd_online`, открыть Query Tool для этой базы и выполнить файлы по порядку. Для `psql` команды из каталога `05-Архитектор БД` такие:

```powershell
createdb -U postgres podezd_online
psql -U postgres -d podezd_online -v ON_ERROR_STOP=1 -f "sql/01_create_database.sql"
psql -U postgres -d podezd_online -v ON_ERROR_STOP=1 -f "sql/02_test_data.sql"
psql -U postgres -d podezd_online -v ON_ERROR_STOP=1 -f "sql/03_queries.sql"
```

Первый файл создаёт 11 таблиц, ограничения и индексы. Второй добавляет два дома, три квартиры, трёх жителей и двух сотрудников. Анна и Иван живут в одной квартире дома 10, Мария — в доме 12. К MAX подключена только Анна. В данных есть заявка, авария и сообщение по дому. После заполнения у Анны три уведомления, у Ивана два, у Марии ни одного. Это позволяет проверить разделение по домам и рассылку нескольким жильцам квартиры.

Третий файл содержит выборки для кабинета и диспетчерской, а также примеры изменения статуса и резервирования уведомлений. Примеры изменений заканчиваются `ROLLBACK`, поэтому данные остаются исходными. Скрипты создания и заполнения предназначены для однократного запуска в пустой базе. Тестовые хеши, коды и идентификаторы MAX — заглушки, не рабочие учётные данные.

## Какие данные нужны для сценариев

| Сценарий | Хранение и обработка |
| --- | --- |
| БП-1, ПИ-1. Регистрация по коду | Сервис находит квартиру по отпечатку кода. После подтверждения адреса создаёт `accounts` с ролью жителя. Телефон нормализуется перед записью. Уникальный ключ предотвращает две регистрации с одним номером. |
| БП-2, ПИ-2. Подключение MAX | Сервис выдаёт случайный токен со сроком действия. После подтверждения со стороны бота одной транзакцией помечает действующий токен использованным и сохраняет `max_chat_links`. Повторное событие для использованного токена уже не меняет привязку. |
| БП-3 и БП-4, ПИ-3–5 и ПИ-9–10. Авария | Диспетчер публикует аварию, переносит срок или отмечает устранение. Транзакция меняет `outages`, добавляет строку `outage_events` и создаёт уведомления для жителей нужного дома. Устранённые аварии доступны в истории. |
| БП-5, ПИ-6–7 и ПИ-11. Заявка | При подаче создаются `tickets` со статусом «Новая» и первая строка `ticket_events`. Смена статуса сохраняет новый статус, автора действия и время. Уведомление создаётся только для автора заявки. Фото хранится в той же строке и загружается по запросу при открытии карточки. |
| БП-6, ПИ-8 и ПИ-12. Сообщение по дому | Сервис сохраняет `house_notices` с домом, текстом и автором, затем создаёт по одному уведомлению для каждого жителя дома в той же транзакции. |
| БП-7, ПИ-13–14. Дом и коды квартир | Администратор добавляет дом и квартиры одной транзакцией. Повторный экспорт кодов доступен администратору. Число квартир получается из `apartments`. |

## Доставка уведомлений

Запись в `notifications` видна в кабинете сразу после фиксации транзакции. Если к аккаунту привязан чат MAX, начальный статус — `pending` и отправка доступна сразу. Для жителя без привязки используется статус `unlinked`.

После подключения MAX новые уведомления ставятся в очередь. Старые записи `unlinked` остаются в кабинете; автоматическая рассылка накопленной истории не предусмотрена.

Фоновый обработчик резервирует строки небольшой пачкой через `FOR UPDATE SKIP LOCKED`, переводит их в `processing` и задаёт срок резерва. Внешний вызов выполняется после фиксации этой транзакции. По результату обработчик записывает `sent` или планирует повтор через `next_attempt_at`. После исчерпания попыток ставится `failed`. Задание с истёкшим резервом снова доступно обработчику. Результат записывается только владельцем актуального резерва, по совпадению сохранённого `lease_until`. При обрыве связи после приёма сообщения MAX возможна повторная доставка.

Для цели «до 1 минуты» требуется контролировать задержку от публикации аварии до подтверждения MAX при нагрузке до 2 000 жителей. Схема поддерживает очередь и повторные попытки. Время доставки зависит от скорости обработчика и доступности MAX.

## Доступ, история и резервные копии

- Пароль хранится в виде стойкого хеша с солью. Минимальная длина проверяется до хеширования. Для токена MAX хранится только его хеш.
- Для регистрации по коду квартиры используется HMAC-отпечаток нормализованного кода. Зашифрованная копия нужна для выдачи кодов администратором. Ключи шифрования и HMAC хранятся в конфигурации сервиса вне БД.
- Для жителя дом определяется через его квартиру. Сервис фильтрует аварии и сообщения по дому, заявки и уведомления по учётной записи. Смена статуса, публикация и выгрузка кодов требуют проверки соответствующей роли.
- При конкурентной смене статуса заявки или аварии сервис блокирует строку объекта перед проверкой перехода. Текущий статус, история и уведомления записываются вместе. История сохраняется для разбора действий, а выборки списков используют индексы текущего состояния.
- Внешние ключи проверяют существование записей, а `CHECK` — допустимые значения внутри строки. Принадлежность квартиры автору заявки, роль исполнителя, адресатов рассылки и переходы статусов проверяет сервис в той же транзакции. Прямой доступ жителей к таблицам не предоставляется.
- Резервное копирование PostgreSQL выполняется ежедневно. Копия включает вложения заявок. Восстановление проверяется на отдельном экземпляре PostgreSQL с доступом к требуемым ключам из защищённого хранилища.
